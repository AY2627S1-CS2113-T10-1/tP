ScheduleFlow implementation contract
Five member MVP handoff
Contract version 1 • 27 September 2026 • Java 25
Build the MVP against this contract so that all five portions can be implemented independently and connected without changing their public interfaces. It specifies ownership, classes, method signatures, command behaviour, planning rules, persistence and acceptance checks. The attached ScheduleFlow user guide, CS2113-T10-1.docx, is the requirements source. Where that guide conflicts with itself or leaves a rule undefined, the decisions in this document are the proposed implementation baseline.
This is an implementation specification, not completed application code. The team should commit the shared declarations first, then implement the five roles. Keep public names and signatures unchanged unless all affected owners agree to update this document and their callers together.

Read sections 1 to 3 together. Implement your role’s exact declarations and behavioural rules. Use sections 14 to 16 to connect the application and verify it. All source paths below are relative to src/main/java; test paths mirror the package structure under src/test/java. The package root is scheduleflow. Keep the team’s existing build system; target Java 25 and use JUnit 5 for the listed tests if it is already the course setup.
API blocks list required public constructors, record components and methods. Method bodies and imports are omitted. Put each top level public type in its own file, except the explicitly nested Command records. Unlisted implementation helpers should be private. 1 Decisions that resolve the guide
These decisions deliberately correct or complete the guide. Update the user guide to match them before release. Source references use its exact feature headings because its examples are more reliable to identify by heading than by pagination.
Guide issue
Contract decision
Notes use T1 and C1, but lists and delete examples use bare numbers
Always display and accept T1 and C1. Reject bare numbers, leading zeroes, wrong prefixes and unknown IDs. Compare the numeric suffix when ordering.
Study hours appear only in the schedule example
Study windows are 08:00 to 22:00 every local calendar day, including weekends. These are fixed MVP constants.
All timeslots must be 30 minutes, but deadlines include 23:59
Task and commitment durations must be positive multiples of 30 minutes. Commitment starts must be on :00 or :30. Deadlines may be any minute. A session must end at or before its deadline.
Earliest free periods conflict with the example that leaves 08:00 to 10:00 empty
Use earliest deadline first, then numeric task ID, and fill the earliest free 30 minute slots. Tasks may split around commitments or across days. The corrected example is in section 10.
Planning describes an error, while the FAQ and schedule describe unallocated work
Keep a partial plan when work does not fit. Print each task’s unallocated minutes. A completely blocked task remains fully unallocated. This is a valid planning result, not a failed command.
Completed tasks are mentioned without a completion command
Every stored task is unfinished. Deleting a task is the MVP way to remove completed work. Planning and elapsed time never reduce its stored duration. No done flag or completion command.
One year from first startup requires destructive resets
Replace this with a rolling calendar year from each add or plan operation. No first startup date is stored and no reset is required. Section 2 defines the exact boundary.
Autosave promises no change on failure; exit implies another save
Save each valid mutation before publishing it to memory. Exit and end of input do not save again. Print Goodbye for now! on normal exit.
No tasks and no current plan are ambiguous
Running plan always creates a plan, including when the task list is empty. Print No tasks to schedule. Such a plan can still display commitments and free time.

The original add examples use September 2026 dates that may already be past when someone runs the app. Keep fixed dates in automated tests with a fixed clock; use future dates in the released guide. Fix the missing line breaks in commitment add examples as editorial corrections.
2 Shared rules and time semantics
State and identity
Task and commitment IDs have separate positive integer sequences. A new store starts at T1 and C1. Successful deletion never reuses an ID. A failed add consumes no ID. The next counters persist even when all records are deleted. Numeric suffixes are int values; reject an add before incrementing if its next counter is Integer.MAX_VALUE.
All records and service return values are immutable. Copy every incoming list with List.copyOf. Return no mutable collection, live view or internal map. Null fields and null list elements are invalid. Snapshot contains the saved domain data; AppState contains the current Snapshot and an optional temporary Plan. No module uses a static mutable singleton.
Time model
Capture LocalDateTime.now(clock) once per command in CommandDispatcher. Inject Clock into the application; Main supplies Clock.systemDefaultZone(). The other modules receive that captured now and never read the clock themselves. Dates and times represent local wall time, without stored offsets or zones. A change of computer zone reinterprets these values as local times; MVP durations are wall clock minutes, not elapsed instants across daylight saving transitions.
For a captured now, let H be now.toLocalDate().plusYears(1).atStartOfDay(). Task add accepts a deadline strictly after now and at or before H. The plan covers calendar dates from now.toLocalDate() inclusive to H.toLocalDate() exclusive. This is a rolling calendar year, not a fixed 365 day count. The ordinary LocalDate.plusYears leap day adjustment applies.
All intervals are half open: [start, end). A session ending exactly when another begins does not overlap. A commitment may finish at midnight, represented internally as the next date at 00:00; it may not continue past midnight. In commitment lists, display that endpoint as 24:00. Weekly commitments may occur outside study windows; they still participate in commitment overlap validation.
For today’s plan, begin at the later of 08:00 and now rounded up to the next half hour. An exact 10:00:00 boundary stays 10:00; 10:00:01 advances to 10:30. Clamp this cutoff at 22:00. Future dates begin at 08:00. Sessions use only whole 30 minute slots, end by 22:00 and never start before the cutoff. Commitments are never moved.
Validation and failure boundaries
Names are stripped at both ends, preserve internal spaces and Unicode, and must be nonblank. Reject slash and ISO control characters, including tabs and newlines. Duplicate names are allowed; IDs identify records. Validate structural rules in record constructors and temporal rules in TaskService.add. Loading past deadlines is valid: restarting must not lose overdue tasks.
Syntax or value failures, unknown IDs and save failures leave Snapshot, counters, disk data and current Plan unchanged. A successful task or commitment add or delete clears the Plan. List, help, schedule and exit do not change state. A plan command replaces only the Plan; it never changes tasks, counters or disk data.
There is one running writer per data file. Multi process coordination, editing existing entries, task completion tracking, configurable windows and globally optimal scheduling are outside this MVP.
3 Command contract
Accepted input
Commands and prefixes are case sensitive and lowercase. Day tokens are exactly MON, TUE, WED, THU, FRI, SAT or SUN. Trim outer whitespace; inside a command use one or more ordinary spaces as separators. Reject embedded tabs and newlines. A blank line is ignored by App without calling the parser. Quotes have no special meaning and are unnecessary.
Command
Exact format
Help
help
Add task
task add n/NAME due/YYYY-MM-DD HHmm d/MINUTES
List tasks
task list
Delete task
task delete TNUMBER
Add commitment
commitment add n/NAME day/DAY start/HHmm d/MINUTES
List commitments
commitment list
Delete commitment
commitment delete CNUMBER
Generate plan
plan
View schedule
schedule today OR schedule YYYY-MM-DD
Exit
exit

NUMBER is a positive decimal int without a sign or leading zeroes. MINUTES uses the same numeric syntax, then must be a multiple of 30. Task duration may be any such value representable as int; large tasks can remain partly unallocated. Commitment duration must also fit within its one day. There is no arbitrary task or commitment count cap.
Dates must match four digit year, two digit month and two digit day, and be real dates in years 0001 to 9999. Times must be four digits from 0000 through 2359. Use strict parsing with uuuu-MM-dd, HHmm and uuuu-MM-dd HHmm; do not use lenient date rollover or the week based year pattern YYYY. Values stored in records have minute precision, except captured now and Plan.generatedAt, which retain the clock precision.
The parser must consume the entire line. Names extend up to the next required prefix. Since names cannot contain slash, an extra, duplicate, unknown or reordered prefixed field is invalid. Reject trailing input on no argument commands, deletion and schedule. Parse today as a separate Command type; resolve it with the same captured clock value as command execution.
Error presentation
CommandParser rejects malformed syntax, number overflow and invalid date or day tokens using ParseException. For a recognised command, its usage field is that command’s exact format above; otherwise it is Type help to see available commands. App prints Error: MESSAGE followed by Expected: USAGE. Task and commitment domain validation uses ValidationException; file failures use StorageException. Those errors print one Error: MESSAGE line, with no success text and no state change.
Error wording can be made clearer, but the tests must verify the rejected condition and unchanged state. Public success text, identifiers, schedule labels and empty messages in section 13 are the common output contract. Never print a Java stack trace for an ordinary user error.

5 Commitment member implementation

public record Commitment(int id, String name, DayOfWeek day,

    public int endMinuteOfDay();
    public boolean overlaps(Commitment other);
}

public final class CommitmentService {
    public CommitmentService();
    public Snapshot add(Snapshot state, String name,
                        DayOfWeek day, LocalTime start,
                        int minutes);
    public Snapshot delete(Snapshot state, int commitmentId);
    public List<Commitment> list(Snapshot state);
}
The record constructor requires id > 0, nonnull day and start, zero seconds and nanoseconds, and start minutes equal to 00 or 30. Normalize the name and validate a positive multiple of 30 duration. Compute the start minute as start.getHour() * 60 + start.getMinute(). Reject durationMinutes > 1440 - startMinute; use this subtraction form to avoid addition overflow. A full day commitment at 0000 with duration 1440 is valid.
displayId returns C plus id. endMinuteOfDay returns startMinute + durationMinutes in the range 30 to 1440. It is an int rather than a LocalTime so that midnight is not confused with the beginning of the same day.
overlaps returns false for different weekdays. For the same weekday it returns true exactly when thisStart < otherEnd and otherStart < thisEnd. Adjacent intervals are allowed. Perform overlap checks on the complete commitment intervals, including hours outside 08:00 to 22:00. Names and IDs do not affect the overlap test.
add allocates state.nextCommitmentId(), constructs and validates a candidate, rejects it if it overlaps any existing commitment, then returns a copied Snapshot with only the commitment list and its counter changed. If there is a clash, the error should identify the existing Cn. Guard counter overflow as specified for tasks. Delete, counter preservation and failed operation rules are the same as TaskService, using commitment IDs.
list returns a copied list sorted by weekday Monday through Sunday, then start time, then numeric ID. The displayed identifiers remain the original Cn values; they are never replaced by row numbers. Deleting a commitment removes its entire weekly series.
Completion checks
CommitmentServiceTest must cover same day overlap, containment in both directions, identical intervals, adjacent endpoints, same time on different days, unaligned start, end exactly at midnight, end after midnight, overlap outside study hours, ordering and unknown deletion. Include a full day commitment and verify that the planner later blocks the whole study window.

Snapshot.empty returns empty immutable lists and both counters equal to 1. The canonical constructor copies both lists, rejects nulls, duplicate IDs within either type, nonpositive counters, or a counter not strictly greater than every existing ID of its type. Check pairwise Commitment.overlaps and reject overlaps. T1 and C1 may coexist. Preserve list order in Snapshot; operations needing a particular order sort their own copied views. Models already validate their individual fields.
Do not apply future deadline or rolling horizon validation while loading. Past tasks remain useful, and clock changes must not corrupt a previously saved file. Structural validation failures from record constructors are caught inside decode and translated into StorageException with the line number or affected record where available.
FileStorage resolves its supplied path to an absolute normalised path. Main passes Path.of("data", "scheduleflow.txt"), so the save location is relative to the process launch directory. The constructor performs no I/O. A definitely absent file means Snapshot.empty; an unreadable file, directory in place of file or malformed file is a startup error, not an empty store.
StateCodecTest covers round trips, Unicode and pipe names, empty list counters and malformed content. FileStorageTest covers first launch, restart and failure before replacement. Printing uses a fake Storage to test rollback.
7 Save format and transaction rules
File format version 1
Use UTF 8 text. Encode with LF endings and one final newline; decode LF or CRLF with an optional final newline. Reject interior blank lines, malformed UTF 8, unknown record kinds, extra columns, duplicate headers, unsupported versions or invalid records. Header and NEXT must be the first two lines. The remaining records may be read in any order; encode TASK rows by ascending ID, then COMMITMENT rows by ascending ID.
SCHEDULEFLOW|1
NEXT|2|2
TASK|1|RHJhZnQ|2026-09-22T18:00|180
COMMITMENT|1|TGVjdHVyZQ|MON|10:00|120
This example stores T1 named Draft and C1 named Lecture. NEXT contains nextTaskId then nextCommitmentId. TASK columns are kind, numeric id, encoded name, deadline, remaining minutes. COMMITMENT columns are kind, numeric id, encoded name, day token, start, duration. Dates and times here use strict uuuu-MM-dd'T'HH:mm and HH:mm formats, distinct from the CLI input format.
Encode each normalized name as unpadded URL safe Base64 of its UTF 8 bytes. Decode strictly; reject invalid UTF 8, invalid Base64 and a noncanonical Base64 spelling. Names must already be normalized: reject a decoded value that differs from InputRules.normalizeName(value). This avoids silently changing persisted text. Pipe is allowed inside names because it is encoded; slash is still forbidden by the domain rule. Numeric fields are positive decimal ints without signs or leading zeroes. Do not store plans, output text, absolute paths or a first startup timestamp.
Load and save algorithms
load reads the complete file and calls decode, constructing a candidate Snapshot before returning it. Never partially load or silently drop bad rows. A load failure makes App print a clear error and terminate with status 1 before accepting commands. Leave the file untouched so the user can repair or restore it.
save first encodes the full candidate. Create the parent directories if absent. Write the bytes to a uniquely named temporary file in the same directory as the target. Flush and close it; use FileChannel.force(true) before closing the channel. Replace the target using Files.move with ATOMIC_MOVE and REPLACE_EXISTING. Only return successfully once replacement succeeds.
If atomic replacement is unsupported or fails, report StorageException and keep the existing target. Do not silently fall back to truncating the target or a non atomic replacement, since that breaks the promised transaction. This MVP therefore requires a local filesystem/provider that supports atomic replacement at this path. This strategy is intended to prevent partial files during ordinary failures; it is not a guarantee against every hardware or power failure.
Attempt temporary file cleanup on failure. After a successful replacement, do not turn an unrelated cleanup issue into a reported failed transaction. No file deletion or extra operation after the successful move may cause save to report failure. Creation of an empty parent directory or an orphan temporary file on an unsuccessful save does not count as a committed domain change.
The dispatcher follows candidate → save(candidate) → state.commit(candidate) → success output. This order is mandatory. Service and codec validation must have completed before file replacement. state.commit is an in memory assignment and plan reset only; it cannot perform fresh fallible validation or I/O after save.

TimeRules has a private constructor. horizonEnd implements section 2. eligibleStart accepts a date from now’s local date through the day before H, rejects any other date, returns 08:00 on a future date, and today returns the rounded cutoff clamped to [08:00, 22:00]. It must account for seconds and nanoseconds when rounding.
StudySession requires a positive task ID, nonnull times on the same date, aligned half hour endpoints, start < end, and endpoints inside that day’s study window. minutes returns the exact integer wall clock difference. UnallocatedWork requires a positive task ID and positive multiple of 30 minutes, a valid normalized task name, nonnull minute precision deadline and nonnull reason. Its taskName is copied from the source task.
Plan copies both lists, requires nonnull metadata and source, and uses horizonEnd equal to TimeRules.horizonEnd(generatedAt). sessions are chronologically sorted, with numeric task ID as a final tie breaker; unallocated follows deadline then numeric task ID. isComplete means unallocated.isEmpty(), including an empty task list. The planner is responsible for the cross record invariants in section 9; consumers must not repair or reorder a Plan. source is the immutable input Snapshot used to generate it.
9 Optimizer algorithm contract
public interface Planner {
    Plan generate(Snapshot state, LocalDateTime now);
}
public final class EarliestDeadlinePlanner implements Planner {
    public EarliestDeadlinePlanner();
    public Plan generate(Snapshot state, LocalDateTime now);
}
Implement a deterministic earliest deadline greedy allocator. This is the MVP’s named optimizer; it does not claim to minimize fragmentation or maximize the number of completed tasks. Use no network, console output, file access or randomness.
1. Enumerate every 30 minute study slot in the horizon, in increasing start time. Skip today’s slots before TimeRules.eligibleStart. There are 28 potential slots per complete day and at most 10,248 across a leap year. Instantiate weekly commitments on the matching weekday and mark any intersecting slot unavailable. Commitments outside the study window have no effect on capacity.
2. Sort all tasks by deadline ascending, then numeric id ascending. For a deadline at or before now, add its full remainingMinutes as DEADLINE_PASSED. For a deadline after H, add the full amount as OUTSIDE_HORIZON. Do not allocate either task; these cases can arise from restored data or clock changes.
3. For each other task, scan the still free slots in chronological order. A slot is eligible only if its end is at or before the deadline. Assign slots until the task’s minutes are filled or no eligible slot remains. Keep assignments already made even if the task cannot be fully accommodated, then continue to the next task.
4. For any positive remainder, emit exactly one UnallocatedWork with INSUFFICIENT_CAPACITY. The remainder equals stored remainingMinutes minus allocated slot minutes; it is not the whole original duration when some slots fit.
5. Merge consecutive assigned slots for the same task on the same date into one StudySession. Never merge across a commitment, unassigned gap, another task or midnight. Sort sessions globally by time and construct the Plan with the input Snapshot and captured now.
A straightforward scan costs O(number of tasks × number of horizon slots), plus commitment matching and task sorting. A boolean array or ordered slot list is sufficient. Avoid enumerating every minute or growing a search beyond H. This bound remains small even when a task requests an extremely large int duration. Use int subtraction for remaining work and long for aggregate totals.
Required invariants
Every session refers to an existing source task, begins at an eligible boundary, lies inside the planning range, ends no later than its task deadline, and overlaps neither a commitment nor another session. For each task, allocated minutes plus unallocated minutes exactly equals the source remainingMinutes. Fully scheduled tasks have no unallocated entry. Names and deadlines in unallocated entries match the source task. All stored task durations remain unchanged.
Calling generate twice with equal Snapshot and now must return equal Plan records. No tasks returns a Plan with zero sessions and zero unallocated entries while retaining source commitments. All blocked slots returns a Plan with zero sessions and a full remainder for every otherwise eligible task.
EarliestDeadlinePlannerTest covers ties, deadline and cutoff boundaries, splitting, merging, blocking, partial fits, long durations and determinism. Assert minute conservation and no overlap for each fixture.
10 Schedule projection and corrected example
public enum SlotKind { TASK, BUSY, FREE, UNPLANNED }
public record ScheduleEntry(LocalDateTime start, LocalDateTime end,
                            SlotKind kind, String reference,
                            String name) {
}
public record ScheduleView(LocalDate date, LocalDateTime generatedAt,
                           List<ScheduleEntry> entries,
                           List<UnallocatedWork> unallocated) {
}
public final class ScheduleService {
    public ScheduleService();
    public ScheduleView forDate(Plan plan, LocalDate date);
}
forDate rejects dates outside [plan.generatedAt().toLocalDate(), plan.horizonEnd().toLocalDate()). It builds a full 08:00 to 22:00 view for the requested date from plan.source commitments and stored sessions. It does not regenerate or use the current clock. A plan remains a snapshot even after its sessions are in the past.
Classify each half hour slot as BUSY when covered by a commitment, TASK when assigned a session, UNPLANNED when before the generation cutoff on the generation date, and otherwise FREE, in that precedence order. BUSY and TASK cannot coincide in a valid Plan. UNPLANNED explicitly means the period was too early to allocate when this plan was generated. It does not mean available study time. Clip commitment occurrences to the study window; a 07:30 to 09:00 commitment displays 08:00 to 09:00 here.
Merge adjacent entries only when kind, reference and name all match. BUSY reference is Cn and TASK reference is Tn; their names come from plan.source. FREE and UNPLANNED have empty reference and name strings, never null. ScheduleEntry validates nonnull fields, aligned times within one study window, start < end, and those reference rules. ScheduleView copies both lists. Its entries cover the window without gaps or overlaps; its unallocated list is the entire plan’s unallocated work in the same order as Plan, even when a task is due on another date.
Corrected guide example
Given now = 2026-09-21 07:00, T1 needs 180 minutes by 2026-09-22 18:00, C1 is Monday 10:00 to 12:00 and C2 is Monday 12:00 to 13:00, plan produces:

Generated at: 2026-09-21 07:00
08:00 - 10:00 | [TASK] T1: CS2113 draft (120 min)
10:00 - 12:00 | [BUSY] C1: CS2113 lecture

AppState stores a private Snapshot and an initially empty Optional<Plan>. commit assigns a previously saved candidate and clears the Plan. replacePlan sets the Plan without changing Snapshot. Callers guarantee that plan.source equals the current Snapshot. The dispatcher captures now once and follows the routing table in section 14. execute returns output instead of printing it; only Exit returns shouldExit = true. 12 Application lifecycle continued
App creates one CommandParser, TextRenderer, TaskService, CommitmentService, EarliestDeadlinePlanner and ScheduleService, and uses these with its injected Storage and Clock to build the dispatcher. These dependencies have no hidden I/O during construction.
1. Call storage.load once. On StorageException, print renderer.error with the load failure, then return 1. Never continue with an empty Snapshot after a corrupt or unreadable file.
2. Construct AppState from the successfully loaded Snapshot. No Plan is restored. Print no success claim about a save on startup.
3. Prompt, read a line and skip blank lines. If end of input occurs, print renderer.exit and return 0. Do not save on end of input.
4. Parse, execute, then ui.write the response output. If shouldExit is true, return 0.
5. Catch ParseException and print renderer.parseError. Catch ValidationException or StorageException and print renderer.error. Continue the loop with the previous state after a rejected operation. On input IOException, print a read error and return 1. Do not swallow unexpected programming exceptions as ordinary validation errors.
Main constructs FileStorage(Path.of("data", "scheduleflow.txt"), new StateCodec()), Clock.systemDefaultZone() and a ConsoleUi around UTF 8 stdin and stdout. It calls new App(storage, clock, ui).run() and supplies that result to System.exit. Keep process exit out of App and all unit tested services. Ignore no unexpected CLI flags silently: this MVP takes no command line arguments; Main reports a usage error and exits 1 if args is nonempty. Configure the JAR manifest entry point as scheduleflow.Main.
Ownership boundaries for independent implementation
The Task and Commitment services only create candidates. FileStorage only loads and writes snapshots. Planner and ScheduleService only return planning records. Imports may cross these public API boundaries; no module may reach into another member’s private data structures.

13 Plan and schedule output continued
Plan output
If plan.source().tasks().isEmpty(), return exactly No tasks to schedule. If tasks exist and isComplete is true, return Study plan generated successfully! Type 'schedule today' to view your sessions.
If unallocated work exists, return the following shape. Totals are whole plan totals and use long arithmetic. The individual rows follow Plan.unallocated order. Zero scheduled minutes is still a partial result with all work listed.
Study plan generated with unallocated work.
Scheduled: N min | Unallocated: M min
Tn: NAME | Unallocated: K min | Reason: REASON
Map DEADLINE_PASSED to deadline passed, OUTSIDE_HORIZON to outside planning horizon and INSUFFICIENT_CAPACITY to insufficient time before deadline. Repeat the task row once per unallocated task. Do not print Generating study plan... as a separate premature success indication; the synchronous dispatcher returns the completed result.
Schedule output
Use the heading and Generated at line shown in section 10, then entries in chronological order. BUSY rows include ID and name. TASK rows include ID, name and that row’s session minutes. FREE and UNPLANNED rows have only the bracketed label after their time range. If any UNPLANNED entry appears, add: UNPLANNED periods were before the planning cutoff.
For any nonempty view.unallocated, append a blank line, the heading Unallocated work for the whole plan:, and the same unallocated task rows used by plan output. This footer is intentionally plan wide, so a selected date does not hide unfinished work due elsewhere. No footer is printed for an empty unallocated list.
If there is no current Plan, the dispatcher returns noPlan without calling ScheduleService. A valid date outside the plan’s range produces ValidationException with a message including the earliest and latest allowed calendar dates and a suggestion to run plan again when appropriate. The renderer must never fabricate empty free schedules outside the plan’s horizon.

Dependency and ownership rules
Task owns common validation and Task. Commitment owns Commitment. Save owns Snapshot, which depends on both models.
